# 工作流程穩定性改善計畫

日期：2026-11-08  
狀態：三批均已實作並完成完整離線回歸；真實 provider／硬體與 live 工作流程驗收尚未執行。  
原始檢查基準：`6e0396c`；最終整合驗證結果見文件末尾。後續實作前仍須重新核對程式與進行中的任務。

## 目標與原則

降低每輪開發所需的人工救援，讓核准、模型探索、審查與交付有可核對的證據。
保留現有狀態機與交付二次確認，不另建流程框架、不新增依賴、不寫死模型版本。
分三批實作與驗收，先完成核准時序，再處理模型探索，最後處理權重調整。
本計畫不授權變更目前任務狀態、接受既有變更、刪除 worktree、提交或合併。

## 已核對的問題

1. `state.py` 的核准紀錄包含決策、時間、request／plan hash，但缺少核准當時的檔案基線與受控實作開始紀錄。`reviewer.py` 明確提醒模型不能以核准紀錄證明首次編輯時序，因此新任務仍可能反覆要求 owner 處置歷史疑義。
2. `cloud_routing.py` 將 Codex 命令失敗、逾時與解析錯誤統一回傳空模型清單；下游會顯示沒有允許的模型。AGY 模型清單查詢上限為 60 秒。Tev1 逾時僅對當次候選組合快取回退結果，其他組合仍可能再次等待。
3. `manager.py` 的權重 schema 未要求 `reason`，驗證器僅檢查 adjustments 是陣列；無理由建議仍可進入設定更新。既有單次變動幅度限制不能替代有效理由與輸入驗證。

## 第一批：核准與受控實作的證據

### 影響範圍

- `orchestrator/core/state.py`：核准紀錄、實作起點、證據驗證及保存。
- `orchestrator/main.py`：核准、修訂、繼續與清理入口的紀錄生命週期。
- `orchestrator/roles/developer.py`：首次可寫操作前的共用檢查。
- `orchestrator/roles/reviewer.py`：使用結構化證據，區分已確認、缺失及不匹配。
- 對應狀態、Developer、Reviewer、CLI／GUI 測試；GUI 沿用共用核准入口，只有發現漏接時才修改 `orchestrator/gui.py`。

### 實作步驟

1. 追查所有核准、修訂與寫檔路徑，包括模型直接編輯 worktree，以及由 Orchestrator 套用回覆的路徑。列出哪些動作真的能修改任務檔案。
2. 在既有執行鎖內保存核准識別、request／plan hash、任務範圍及檔案基線。基線至少能區分內容、缺檔與檔案型態；重用既有快照能力，避免另造相同機制。
3. 在第一次可寫呼叫之前持久化實作開始紀錄，引用同一核准識別並核對基線。紀錄保存失敗時不得開始可寫操作。以受控程式順序與紀錄關聯驗證先後，時間戳只供診斷，不單靠系統時鐘比較。
4. 區分尚未開始與已開始的實作。重啟、同範圍修訂及重試應沿用有效紀錄；不得拿核准前基線與已合法修改的檔案直接比較，造成每次重試都失效。
5. request、plan 或授權檔案範圍改變時，依現有規則重新取得適用核准。保留原核准與實作起點，後續 approval 不得覆寫成虛假的首次核准時間。
6. Reviewer 接收程式驗證結果及其適用範圍。有效證據足以確認本次受控實作時，不再要求重複處置相同時序疑義；有真實範圍變動或缺少證據時仍停止。

### 舊任務與限制

- 舊任務缺少紀錄時標示「未知」，不得補造首次編輯時間或宣稱歷史授權已核實。
- 沿用既有「展示接受範圍 → 接受現有變更並重新審查」處理舊任務；內容改變後原接受快照失效。
- 證據只涵蓋 Orchestrator 管理的操作，不能證明外部編輯器在所有時間都未改檔。
- 核准基線已包含的變更須明確呈現；一般實作核准不自動等同接受所有既有變更。

### 驗收案例

- 正常核准後實作，Reviewer 可取得相符證據，不要求第二次歷史核准。
- 未核准、範圍變動、核准後首次實作前被外部改檔：禁止可寫操作並顯示具體原因。
- 紀錄寫入失敗、核准後中斷、實作開始後中斷、同範圍重試：不跳過保護、不覆寫歷史。
- 舊任務與已接受快照：保持既有人工處置與內容變動失效規則。
- CLI 與 GUI 產生相同證據；測試通過與 owner 接受都不取代交付二次確認。

## 第二批：模型探索故障可診斷、可恢復

影響：`cloud_routing.py`、`backends.py`、路由失敗分類的共用呼叫端及相關測試。

1. 分開表示命令逾時、命令退出失敗、格式不符、有效空清單及全部被政策排除。錯誤訊息保留有限長度的診斷資訊，不輸出模型清單中的整份系統指示或憑證。
2. 失敗結果不得覆寫最後成功清單。是否容許短期舊清單須有明確期限、提示與候選重新驗證；不可靜默永久沿用過期模型。
3. 對探索失敗使用有限重試與短暫冷卻。探索失敗不得直接當成模型契約失敗或永久不可用；恢復後能重新探索。
4. Tev1 連續逾時時採用可恢復的 endpoint 冷卻，避免同一輪模型、backend、reasoning 評分逐次等待。回退仍遵守現有候選與禁用模型政策。
5. 不以無限制提高 timeout、偷偷改用 CLI 預設模型或寫死版本解決。

驗收：使用 mock 驗證逾時、非零退出、格式錯誤、空清單、全部禁用、冷卻恢復、模型新增／移除與快取到期。檢查呼叫次數有界，且 astra／argon／fabel 等既有禁用政策仍有效。

風險：冷卻太長會延後恢復；舊清單可能含已移除模型。實作前根據現有設定決定最少必要參數，不新增大量調校選項。實際硬體延遲需另做小量驗證，離線測試不能宣稱服務已恢復。

## 第三批：權重調整必須有依據

影響：`orchestrator/roles/manager.py`、既有權重驗證／儲存共用函式及相關測試。

1. 明確定義允許的 role／level、有限數值、變動幅度及非空理由，並在程式端驗證，不只依賴模型遵守 schema。
2. 建議須能對應本輪已有的執行證據；沒有足夠證據就維持原權重。理由文字本身不能當成證據。
3. 拒絕 NaN、Infinity、布林值、未知角色及重複條目，避免一次回覆累加調整繞過幅度限制。
4. 保存原值、新值、理由及對應證據，沿用既有報告位置；完整驗證後才寫入設定，寫入失敗不得留下半份設定或記憶體／磁碟不一致。
5. 不回溯重算既有權重，不讓這項附加工作重跑已完成的開發或驗收。

驗收：缺理由、無證據、非法值、重複角色均不更新設定；有效建議符合上限且保留其他設定；寫入失敗保留可用原設定。

風險：更嚴格的驗證會減少自動調整次數。這是預期行為，不應再增加模型呼叫來強求一份調整建議。

### 第三批實作與離線結果（2026-11-08）

- Schema 與程式端共同限制 `rd`／`qa`、三種 level、最多六筆建議及權重範圍；非空理由與非空 `evidence_ids` 必填。拒絕 NaN、Infinity、bool、數字字串、未知角色、重複角色／level、重複證據與額外欄位。整批通過才保存，原本的單次變動幅度與三位小數慣例保留；最後再次限制幅度，避免 rounding 跨越較小的自訂上限。

- 共用設定保存先複製並驗證新值，以同目錄暫存檔、flush／fsync 及 atomic replace 提交；成功後才更新記憶體。原值、新值、理由與完整引用證據和單筆 `last_worker_weight_review` 同一交易保存，保留其他設定與 vendor scorecard。沿用 `final_report.md`，報告亦使用原子替換，寫入失敗保留原報告。
- 相同 run 重新啟動或交付重試時沿用已提交 audit，只補報告，不再次調權或呼叫 Manager；已準備 artifacts／已交付的入口亦可補報告。Audit 僅保留最近一個 run，不建立新歷史框架；正常循序流程的 UUID 與封存機制維持唯一身份。人工還原跨多輪舊 state 不在此去重保證內。
- 新增 `test_weight_review.py`，更新兩個既有 Manager 測試的本輪證據；聚焦權重、scoring 與 telemetry 回歸為 **93 passed、308 deselected**（3.02 秒）。涵蓋非法整批拒絕、本輪／角色／backend 對應、幅度與 rounding、600 筆歷史的有界抽樣、寫入及部分報告寫入失敗、cleanup 失敗不遮蔽提交、重新載入與報告冪等、契約重試紀錄及 GUI UUID。
- Manager、telemetry、scoring 與新測試已逐檔 pyink 通過，`git diff --check` 通過；完整離線回歸由三批收斂後統一記錄。格式化的多檔 worker 等待已中止，已確認沒有遺留本批 formatter 程序。
