## 目的與範圍

先修正 Multi-Agent Orchestrator 的失敗處理與人工操作流程，再評估是否將個別能力獨立包裝成 skill。預設使用情境是單一使用者、本機 GUI／CLI、一次一筆任務。

此計畫源自唯讀原始碼檢視。尚未執行完整測試、真實模型流程或全面後端與 Git 交付安全審計；執行前須重新確認程式現況。不能將本計畫視為產品已可發布的證明。

商業邊界：專案仍屬實驗性 harness，作者未承諾持續產品支援、修復或維護。Agensi 的流量、分潤與平台條款尚未查證；本計畫不包含上架、簽約或對外承諾。

## 第一批：停止無效修復循環與錯誤狀態回報

### 1. QA 無效回答不得變成修復任務

- 現況：`orchestrator/roles/qa.py` 將缺少 `QA_STATUS` 的回答算作反對票。即使測試成功，無關回答仍可能導致 Developer 扣分與 `FIX-QA` 任務。
- 影響檔案：`orchestrator/roles/qa.py`、`test_orchestrator.py`；如涉及共用回應驗證，先追蹤其呼叫端再決定最小修改範圍。
- 計畫：分開處理通過、有具體缺陷與回應無效。無效回答有限次重試，耗盡後保留診斷原因；只有有效缺陷才建立修復任務。
- 預期：不再因 QA 回覆專案介紹等無關文字而要求修改檔案，也不將無效回應當成通過。
- 風險：既有投票與評分行為會改變；須保留真實測試失敗不能被模型覆核掩蓋的規則。
- 驗收：測試成功但 QA 回應無效時，不產生假修復任務、不錯扣 Developer 分數、不自動通過；有效否決與真實測試失敗仍正確阻止交付。

### 2. GUI 啟動逾時與背景錯誤回報

- 現況：`orchestrator/gui.py` 在取得鎖並完成 `prepare()` 後才通知啟動成功；準備過程可能查詢 Tev1。超過 10 秒會報沒有取得鎖，但 worker 並未取消，之後仍可能繼續。準備完成後的背景例外未完整回報給使用者。
- 影響檔案：`orchestrator/gui.py`、`test_gui.py`；若需要持久錯誤狀態，先確認現有狀態快照 API 的適用範圍。
- 計畫：分開呈現已接受、準備中、執行中與失敗；耗時準備留在背景，保存並展示 worker 錯誤。處理客戶端斷線，避免次生 BrokenPipe 掩蓋原始問題。
- 預期：不會向使用者顯示操作失敗後，又在背景開始實作；鎖衝突與準備逾時可以辨別。
- 風險：啟動確認時機改變可能造成重複操作；必須保持共用執行鎖及 worker 互斥。
- 驗收：慢速準備、真正鎖衝突、背景例外、重複點擊與客戶端斷線均有對應測試，確保只啟動一個工作流程。
- 更正先前診斷：`Workflow worker did not acquire the execution lock` 不足以證明其他程序占用鎖；目前也可能由準備時間超過等待期限觸發。

### 3. 人工要求修訂時保留否決理由

- 現況：`orchestrator/main.py` 對 Architect 的 revise 將 `plan_revisions` 歸零並移除人工審核內容；`orchestrator/roles/developer.py` 只在計數大於零時加入先前計畫審核意見。人工重新規劃可能遺漏修訂依據。
- 影響檔案：`orchestrator/main.py`、`orchestrator/roles/developer.py`、`test_orchestrator.py`。
- 計畫：將重試額度與待處理審核意見分開保存，讓下一次規劃明確收到本次否決理由。
- 預期：人工要求修訂後，Manager 能處理具體審核要求。
- 風險：舊審核內容殘留可能污染新任務；須明確定義消費與清除時機。
- 驗收：人工 revise 後下一次 Manager 輸入包含指定理由；不混入上一筆任務的內容；重試額度仍符合既有人工決策規則。

## 第二批：操作與可重現交付

### 4. GUI 依狀態提供正確操作

- 現況：頁面固定顯示繼續、通過、修訂、重置與交付，使用者必須理解內部狀態才能選擇；CLI 的清除失敗路由重試選項沒有對應 GUI 操作。
- 影響檔案：`orchestrator/gui.py`、共用決策入口、`test_gui.py`，必要時補 `test_orchestrator.py`。
- 計畫：沿用共用決策邏輯，依狀態提供主要操作與預期結果，例如重試目前任務、依審核意見修訂；執行中防止重複提交。必要時提供有明確說明的失敗路由重試入口。
- 預期：使用者不必每次詢問該按哪個按鈕。
- 風險：簡化按鈕不能隱含批准被否決內容，也不能跳過交付確認。
- 驗收：各暫停來源顯示正確操作；GUI 與 CLI 決策一致；交付保留獨立確認；重置仍說明資料清理影響。

### 5. 離線端到端驗收與 CI

- 現況：本次檢視未發現 `.github/workflows`。現有單項測試不足以單獨證明完整交付流程可靠。
- 影響範圍：現有測試、必要的測試 fixtures、新增 CI workflow；不預設引入新依賴。
- 計畫：使用離線模型替身與臨時 Git repository，驗證提交、規劃、實作、QA、審核、交付預覽、確認合併。加入暫停、重啟及合併衝突保留成果的情境。
- 預期：提交前能攔截流程退化，測試不消耗付費模型額度。
- 風險：CI 的 socket、Git、Python 環境與本機不同；須明確記錄支援環境。
- 驗收：檢查實際提交、合併與狀態結果，不只斷言 mock 被呼叫；CI 不需要真實模型憑證。

### 6. 文件與多語系驗收

- 現況：`README.md` 描述 Architect 達上限後直接實作，與目前暫停人工審核的程式不同。`verify_alignment.py` 以行數與結構比對為主，不能證明命令、連結及內容正確。
- 影響檔案：五份 README、`docs/workflow-fsm.md`、必要的 GUI 使用文件、`verify_alignment.py` 與對應檢查。
- 計畫：以實際 CLI 與狀態轉移為共同核實基準，同步五語文件。檢查命令、連結與程式碼區塊，不要求自然語言翻譯逐行相同。
- 預期：文件能正確引導安裝、繼續、修訂、停止與交付。
- 風險：翻譯同步可能誤刪單一語言版的補充資訊；需先比對差異並保留有用內容。
- 驗收：五語版的關鍵行為與命令一致，連結與範例完整；結構一致不再被宣稱為內容正確的充分證據。
