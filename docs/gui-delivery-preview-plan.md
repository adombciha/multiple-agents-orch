# GUI 交付預覽改善計畫

目標：使用者按一次「展示 Git 影響」，即可看到這次請求的結果、核對變更，並自行決定是否確認交付，全程不必重新整理頁面。

## 現況與範圍

主要入口在 `orchestrator/gui.py`。預覽預設展開，而 `readingProtected()` 會將展開的區域視為正在閱讀。當快照內容改變時，`applyGitUpdate()` 可能延後套用新內容。現有程式已有處理中訊息及確認失效機制；先驗證實際點擊路徑，再決定需要改哪一段。

預計修改 GUI 的交付預覽互動，以及 `test_gui_refresh.py` 的對應案例。沿用既有交付 API、快照 ID、逐項驗收與二次確認。輪詢效能和耗時摘要各自另案處理。

## 實作順序與驗收

1. **建立失敗基準。** 在隔離測試資料中先展示快照 A，保持預覽展開並選取文字，再讓展示請求回傳快照 B。記錄回應 ID、畫面快照 ID、確認按鈕綁定的 ID，以及使用者看到的回饋。若三者一致且結果已清楚可見，回報重現條件與觀察，不為這個假設修改程式。
2. **區分主動展示與背景更新。** 背景輪詢繼續保護焦點、文字選取與捲動位置。使用者主動展示時，沿用按鈕旁的回饋顯示進度；成功後展開並定位本次快照，可用鍵盤直接閱讀。若當時正選取舊內容，保留選取並在操作處提供「查看本次快照」，啟用後直接定位，不要求先收合或按 F5。
3. **確認操作綁定可見內容。** 請求處理中停用重複操作；只有畫面顯示此次快照且符合既有驗收條件時，才提供該 ID 的確認。遇到失敗、回應過時或快照失效，顯示原因與重新展示入口。展示本身不得送出確認。
4. **驗證後交付。** 用既有前端測試覆蓋首次展示、重展相同與不同快照、背景更新期間保留閱讀，以及展示失敗後重試。用實際瀏覽器在隔離任務重走一次「選取 A → 展示 B → 核對 B」，確認只送一次展示請求、確認鍵綁定 B；再以鍵盤操作一次。記錄測試命令、結果與瀏覽器版本。QA 與 Reviewer 通過後，依現有流程展示 Git 影響，由 owner 二次確認。

主要風險是背景刷新搶走閱讀焦點，或畫面仍顯示 A 卻允許確認 B。兩者都列為阻擋交付的回歸條件。瀏覽器驗證使用測試任務，不操作使用中的交付。
